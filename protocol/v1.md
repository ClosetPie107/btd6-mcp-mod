# AgentBridge protocol v1

Transport: same-user filesystem mailbox under the BTD6 research payload:

```text
loader-payload/UserData/AgentBridge/ipc/
├── inbox/
├── processing/
├── outbox/
└── state.json
```

The native adapter publishes one complete JSON file to `inbox/` with a unique filename ending in `.json`. A bridge worker atomically claims it by moving it to `processing/` and queues it for execution from `OnUpdate()` on the BTD6 game thread. The worker publishes `outbox/<requestId>.json` atomically after execution, then removes the processing file. Producers must never edit a published file. Consumers must treat `state.json` and outbox files as immutable.

## Request envelope

```json
{
  "protocolVersion": 1,
  "requestId": "req-0001",
  "kind": "status",
  "issuedAtUtc": "2026-09-05T10:31:48.0000000Z",
  "deadlineAtUtc": "2026-09-05T10:31:53.0000000Z",
  "payload": {}
}
```

`requestId` is 1–128 ASCII letters, digits, `.`, `_`, or `-`. A request is rejected when its protocol version differs from 1 or its deadline has expired. The bridge accepts at most 64 KiB per command file and bounds outstanding commands to 32. Game-thread processing has configurable per-frame time and step budgets; excess requests remain in the inbox.

## Result envelope

```json
{
  "protocolVersion": 1,
  "requestId": "req-0001",
  "ok": true,
  "completedAtUtc": "2026-09-05T10:31:48.1120000Z",
  "result": {},
  "error": null
}
```

Failures have `ok: false` and a structured error:

```json
{
  "code": "UNKNOWN_COMMAND",
  "message": "Command 'unsupported' is not supported by protocol v1.",
  "retryable": false
}
```

Envelope-level errors include `UNSUPPORTED_PROTOCOL`, `INVALID_REQUEST_ID`, `DEADLINE_EXCEEDED`, and `UNKNOWN_COMMAND`. Individual commands return additional structured errors.

The MCP adapter enriches errors with `requestId` when available and a `submissionState`:

- `not_submitted`: validation or mailbox publication failed before submission.
- `rejected`: a correlated response establishes a known pre-execution rejection.
- `submitted_outcome_unknown`: the command was published, but the response is absent, malformed, uncorrelated, or does not establish whether a mutation occurred. A bridge restart during execution also has an unknown outcome.

Unknown outcomes are not automatically retryable. Observe game state before repeating a mutation. A completion-read failure after an accepted round start does not make the start safe to repeat. Response envelope and payload validation execute within the request context, retaining the originating request ID even for null or malformed nested payloads.

Startup recovery never replays files left in `processing`. Each valid interrupted request receives `BRIDGE_RESTARTED`; malformed files are isolated so they cannot prevent recovery of later requests. A valid file whose result cannot be published, or a file that cannot be read, remains for a later startup.

## Read-only commands

### `status`

Returns the bridge/game versions, readiness, active-match and main-menu state, selected hero, automatic-collection setting, and declared capabilities. The current bridge exposes player actions and explicit research controls as well as read-only observation, lightweight round progress, geometry, and performance reports.

`moduleVersionId` is the loaded managed assembly's module version ID, encoded as a hyphenated GUID. It identifies the assembly in this process, not the DLL currently on disk. The adapter requires this field. The testing harness reads the staged PE metadata without loading game dependencies and compares identities before live scenario mutations; deploying another DLL does not change the loaded identity until restart.

### `observe`

Returns the current match snapshot, including stable `mapId`, localized `mapName`, round state, resources, placed towers, hero, abilities, and threat telemetry. Tower entries include three semantic `nextUpgrades` records (`path`, localized `name`, live `cost`, `available`) and nullable `crosspathSlotsRemaining`. Match-dependent values are nullable outside an active game.

### `round_progress`

Returns lightweight match identity, round number/activity, game status, cash, lives, and UI readiness without enumerating towers or bloons. The native adapter uses this command for round waiting and captures one full observation at termination.

### Adapter round waiting

`btd6_start_round` waits by default; `btd6_wait_for_round_end` can wait independently. Their MCP surface is structurally compact: clean rounds cannot request verbose repeated observation state; defeat and timeout retain diagnostic telemetry. A separate full observation retrieves complete state.

Waiting distinguishes `round_cleared`, `victory`, `defeat`, `match_ended`, `ui_blocked`, and `timeout`. A ready-to-start round is not evidence of clearance: the adapter must observe activity ending or advancement of the tracked round. An idle standalone wait can time out with `roundCompleted: null`. Unknown or failed UI returns `ui_blocked`, `completed: false`, `roundCompleted: null`, and the blocker; known automatic transitions continue waiting. The timeout bounds progress monitoring; final observation requests still have their own mailbox deadlines.

### Geometry limits

The geometry producer permits 512 paths and 32,768 aggregate source points. Topology schemas allow up to 512 routes, 32,768 nodes/edges, and 32,768 points per edge. Splitting duplicates segment endpoints, so the aggregate edge-waypoint budget is 65,536. Oversized payloads are rejected rather than silently truncated.

Map coordinates use +X right and +Y down, matching the game's displayed orientation. The renderer applies the same transform to terrain, paths, markers, ranges, and graph overlays; compass north is decreasing Y. No placement or targeting coordinate values are negated.

`find_placement_spots.rankingStrategy` additionally accepts `trackCoverage`; existing ranking objectives/defaults are unchanged. The coverage branch uses the requested tower model range, active non-hidden polylines, line/circle clipping, duplicate/reversed-path removal and collinear-span union. Discovery checks the exact requested `near` center (for every ranking), the coarse grid, and up to 1024 in-bounds range-relative bend-offset samples for coverage ranking. It then re-ranks and refines up to 16 spatially separated seeds over three passes, halving the initial half-grid step each pass to a minimum of 0.5. `search.refinementStep` reports the initial step. All stages share the 4096-native-check cap; budget exhaustion can leave later stages incomplete. Coverage shortlists greedily retain score-ordered candidates separated by at least `max(coarseStep, modelRange / 2)` and may return fewer than `limit` rather than pad with near-duplicates. `totalFound` counts valid discovered candidates before shortlist suppression. Each spot includes range, unique length, angular coverage and bounded per-path intervals (128 paths/512 intervals), with total counts and an explicit truncation flag. `search.coverageBasis` is `active_path_polylines`. Interval fractions are source-polyline fractions, not native bloon progress. This remains a bounded heuristic, not an exhaustive optimum; scores are not LOS, projectile travel-time, targeting or traffic-weighted DPS guarantees.

`supportCoverage` ranking requires 1–20 unique `coverTowerIds`. Candidates are ordered by covered recipient count, total center distance, then track distance. Each candidate exposes covered/uncovered IDs. `inspect_support_coverage` supports placed Monkey Villages and Alchemists and reports recipients, margins, and a warning for empty coverage. `eligibilityVerified` is false: this geometry does not prove native aura/buff eligibility.

### Camo acquisition and collision

`tower_stats` and `inspect_tower` expose `poppingCapabilities.camo` and per-weapon `camo`, replacing the old flat camo flags. Fields are nullable booleans `canDetectCamo`, `canCollideCamo`, `needsDetection`, `canDamageCamo`; source strings `detectionSource`, `collisionSource`, `damageSource`; at most twelve evidence strings; and nullable `reason`. Unknown acquisition/collision semantics remain explicit.

Native target suppliers distinguish bloon acquisition from map-position targeting and flight/movement controls. Camo acquisition and projectile filters are evaluated separately, including traversed damaging explosions and `SyncCamoDetectionWithTowerModel`. A manually aimed projectile can still be blocked by `FilterInvisibleModel`. Effective inspection uses refreshed live tower/attack/projectile state; static evidence is labeled as model-derived, not live.

`canDamageDdt` is nullable and requires one positive native damage source satisfying camo collision/acquisition, Lead and Black immunity checks, and MOAB eligibility. Tower-wide unions of incompatible weapons cannot establish DDT readiness. These fields report capability, not final target-specific DPS.

### Round timing and damage requirements

`round_info.groups[].startSeconds`/`endSeconds` and `durationSeconds` convert native 60-Hz emission frames to simulation seconds, rounded to two decimals. Duration is the last scheduled spawn-window end, not round-clear time. `observe.roundElapsedSeconds` and ability scheduling use the native elapsed tick counter relative to the current native round-start record, independent of wall time and fast-forward. Missing active-round timing is `null`; scheduling fails before submission with `ROUND_TIME_UNAVAILABLE`.

Group `isLead` and `threatIntel.hasLead` retain Lead identity semantics. Group `requiresLeadPopping` and `threatIntel.requiresLeadPopping` report the native Lead damage-immunity bit; DDTs therefore require Lead popping even when `isLead` is false.

## Regular match mode and economy semantics

`start_match` accepts difficulty categories `Easy`, `Medium`, and `Hard`, plus `checkpointPolicy: "assisted" | "none"` (default `assisted`). Assisted mode retains a rolling latest next-playable-round checkpoint and anchors after each fifth completed round. None creates no automatic checkpoints. The result exposes distinct `mapId` and localized `mapName`.

Sandbox uses the native Sandbox identifier outside the regular-mode list and retains the requested difficulty.

Public `mode: "CHIMPS"` maps to the live `ModeType.CHIMPS` identifier (`Clicks` in BTD6 56.3), with difficulty `Hard`. Start results and observations expose the public name `CHIMPS`. `Hard` + `Impoppable` remains the separate higher-price mode with ordinary income permitted. Startup never completes modes or changes unlock progression; `MODE_LOCKED` requires explicit provisioning.

Observation `round` and `endRound` are both one-based; CHIMPS ends at 100. Placed-tower `upgradeCosts` and `nextUpgrades[].cost` apply the game's nearest-$5 rounding after dynamic cost calculation. `nextUpgrades[].name` is the semantic native/localized upgrade identity; unavailable paths have `available: false` and `cost: null`. `crosspathSlotsRemaining` is null until a tier-3+ main path exists.

### Purchases and upgrade batches

Placement checks the current native price and location before creating a tower. Known `INSUFFICIENT_CASH`, `LOCATION_BLOCKED`, and `PRICE_UNAVAILABLE` errors are pre-execution rejections. The error envelope may include an optional `details` object with known `cost` and `cash`; it contains no native game objects.

Both the bridge `upgrade_tower` command and MCP `btd6_upgrade_tower` accept `{ towerId, upgradeSequence, whenAffordable?, round?, delaySeconds?, delayFromNow?, idempotencyKey? }`. The sequence contains 1–15 ordered path indexes, not final tiers. There is no separate `{towerId,path}` primitive. Whole-sequence projected crosspath validation precedes purchases. Immediate sequences execute one native tier per update; partial purchases are never rolled back.

Without scheduling options, execution remains immediate (including between rounds). `whenAffordable: true` alone buys an affordable first step and retains remaining work across rounds. `round`/`delaySeconds` schedule against native simulation time; zero means the target round must start first. `delayFromNow` requires an active native clock and cannot be combined with the other timing fields. Timed work, including timed affordability waits, expires at target-round end. Automatic purchases freeze while paused, UI-blocked, or defeated; requests do not reserve cash. There is one active schedule per tower, at most 32 pending schedules, and 64 retained terminal outcomes.

Results include `completed`, `status`, `appliedPaths`, `appliedSteps`, nullable `tower`/`cash`/`failure`, `scheduleId`, `nextIndex`, `nextUpgradeCost`, and `waitingFor`. Applied steps record the native execution round, simulation seconds, cost and lateness. An unknown native outcome stops execution; an unknown transport response must not be replayed as a fresh sequence. Identical scheduled submissions can reuse `idempotencyKey`; changed input with the same key is rejected. Observe `scheduledUpgrades` for eventual outcomes; `cancel_scheduled_upgrade` stops remaining steps without undoing purchases. Restore/restart/match replacement clear schedules and their match-local idempotency state.

### Geraldo purchases

Capability `geraldoShop` covers `inspect_geraldo`, `can_use_geraldo_item`, `use_geraldo_item`, and `cancel_scheduled_geraldo_purchase`. Inspection requires the active player's native Geraldo and returns `source`, `heroTowerId`, `heroLevel`, `cash` and up to sixteen `items`. Each item reports its exact native `itemId`, localized `name`, nullable `description`, `category`, `targetKind`, nullable native `cost`, stock/max stock, unlock level, replenishment information and native availability. `replenishingFromRound` is one-based or null. Initial-level items report unlock level 1.

`can_use_geraldo_item` accepts `{itemId,target?}` and returns `{valid,code,message,itemId,category,target,cost,cash,stock}`. Targets are strictly `{kind:"point",x,y}` or `{kind:"tower",towerId}`; coordinates must fit finite native floats. `tower_placement` and `track` categories require a point. `tower_target` requires a native eligible owned tower; Cape requires a legal Dart Monkey and fertilizer an eligible Banana Farm. `geraldo_range` (rabbit) and `none` (Rejuvenation) take no target. Rabbit resolves Geraldo's current position internally and uses native eligibility checks.

Eligibility checks isolate the native Geraldo placement-item cache for the requested model and release their temporary item on success, rejection, or exception, restoring any prior selection. Quotes neither consume cash/stock nor leave a selected item that changes subsequent checks. This applies to standalone quotes and eligibility checks before immediate or scheduled purchases, including after checkpoint restoration.

`use_geraldo_item` adds optional `round`, `delaySeconds`, `delayFromNow`, `whenAffordable` and `idempotencyKey`. Without timing or affordability options it executes immediately. Timing follows upgrade scheduling, including active-clock requirements and expiry at target-round end. Affordability-only work persists across rounds. Only insufficient cash is waited on; stock, unlocks and target validity are not silently retried. No resources are reserved. Before execution, native item pricing/stock and recipient eligibility are checked again. Tower-like items use the native Geraldo-tagged tower model and ordinary tower creation with native inventory accounting; consumables use the native Geraldo purchase action. No direct stock, cash or effect setters are used.

Results contain `status` (`pending`, `waiting`, `completed`, `failed`, `expired`, `cancelled`, or `verification_pending`), `purchased`, nullable `scheduleId`, `itemId`, nullable `target`/`cost`, nullable before/after cash and stock, `createdTowerIds`, nullable `affectedTowerId`/`failure`/`waitingFor`, and nullable execution round/seconds. `purchased:true` confirms native accounting; `verification_pending` forbids blind replay regardless of the boolean. Item effects can be inspected with existing tower/ability observation.

`observe.scheduledGeraldoPurchases` contains up to 32 pending purchases plus 64 terminal outcomes. Each entry includes identity, target, affordability/timing fields, status, failure/wait reason and nullable purchase `result`. Old observations lacking the field decode as an empty array. Summary excludes completed/cancelled entries but retains failures, expiry and uncertainty. Native scheduled action reports use `actionKind:"geraldo"`.

Automatic execution freezes while paused/UI-blocked. Update order is due abilities, upgrades, then at most one Geraldo purchase; the Geraldo queue is considered in submission order, without blocking other due entries behind a cash wait. There is no cross-action success dependency. `cancel_scheduled_geraldo_purchase({scheduleId?})` returns `{cancelled,count}`; omit the ID or use `"all"` for all pending work. Restore/restart/match replacement clears schedules and idempotency. Identical keyed requests replay their retained outcome, including after the original timestamp; changed keyed input is rejected. The 512-key limit rejects new keys without evicting protection against replay.

### Corvus spells

Capability `corvusSpells` covers `inspect_corvus`, `cast_corvus_spell`, `set_corvus_spell`, and `cancel_scheduled_corvus_action`. Inspection uses the active player's native Corvus manager and returns `source:"active-simulation"`, `heroTowerId`, `heroLevel`, integer `mana`/`maxMana`, `isRecovering`, `isStunned`, `isManaDraining`, and at most sixteen `spells`.

Each spell reports exact `spellId`, `name`, `kind:"continuous"|"cast"`, one-based `unlockLevel`, `unlocked`, `initialManaCost`, nullable `ongoingManaCost`/`manaDrainIntervalSeconds`/`durationSeconds`/`cooldownSeconds`, `active`, `canCast`, normalized `cooldownPercent`/`activeDurationRemainingPercent`, and nullable `unavailableReason`. `canCast` is actionable readiness, not merely the native flag: an active cast spell or ongoing cooldown blocks another cast even when BTD6's raw flag remains true. Unknown native restrictions remain `native_readiness`, not an invented specific conflict.

`cast_corvus_spell` accepts `{spellId,round?,delaySeconds?,delayFromNow?,whenReady?,idempotencyKey?}`. `set_corvus_spell` additionally requires `enabled:boolean` and accepts only continuous spells. The four continuous IDs are `Aggression`, `Malevolence`, `Spear`, and `Storm`; twelve other native IDs are cast spells. Numeric enum indexes, wrong kinds and all point/tower targets are rejected. Desired-state requests already satisfied complete without native submission. Disabling an active continuous spell uses native cancellation without requiring activation mana. Activation uses the native bridge action in immediate mode; mana, effects and cooldowns are not assigned directly.

Timing follows upgrade/Geraldo conventions. `whenReady` alone can execute immediately or wait across rounds for transient readiness; active cast spells wait through their active period and cooldown. Locked spells are rejected rather than waiting for future levels. Timed work expires at target-round end. No mana is reserved, and completing an enable action does not maintain that state or guarantee future uptime. Automatic execution freezes while paused/UI-blocked and never executes after defeat. Existing scheduled abilities, upgrades and Geraldo purchases run before at most one native Corvus action per update. Pending entries pin the hero identity and resolve current models at execution; replacement heroes cannot inherit them.

Action results include `status` (`pending`, `waiting`, `completed`, `failed`, `expired`, `cancelled`, `verification_pending`), `executed`, `changed`, nullable `scheduleId`/`heroTowerId`, `spellId`, nullable `enabled` (null for casts), nullable integer before/after mana, nullable `spell`/`failure`/`waitingFor`, and nullable execution round/seconds. Completed no-ops have both booleans false. A matching native spell-start event or native active/cooldown transition confirms execution; a void return or mana change alone does not. Unknown native outcomes become terminal `verification_pending` and are never automatically repeated.

`observe.scheduledCorvusActions` contains at most 32 pending entries plus 64 terminal outcomes. Entries include `scheduleId`, pinned `heroTowerId`, `spellId`, nullable `enabled`, `whenReady`, nullable target round/delay, status, wait/failure information and nullable action result. Legacy absence decodes as an empty array. Summaries hide completed/cancelled history but preserve waiting, failed, expired and uncertain actions. Round telemetry uses `actionKind:"corvus"`.

`cancel_scheduled_corvus_action({scheduleId?})` returns `{cancelled,count}`; absent/`"all"` cancels all pending Corvus actions without disabling existing spells. Match reset/restore clears schedules and idempotency. Identical keyed retries return retained outcomes without sliding relative timestamps; changed keyed input is rejected. The 512-key limit never evicts replay protection to admit new keys.

All scheduled-action cancellation commands require an object. Omit `scheduleId` or explicitly use `"all"` to cancel all; a supplied selector must be a nonblank string of at most 128 characters. Unknown or duplicate fields and malformed selectors return `INVALID_ARGUMENT` without cancelling work.

### Round insights

`observe.roundInsights` contains current-attempt telemetry; `observe.roundReport` retains the latest terminal report. Sampling uses native simulation ticks at a requested 0.1-second interval, not wall time. Reports include active/peak bloon and MOAB counts, maximum observed progress, near-exit pressure (progress above 0.85), per-lane pressure, bounded composition/current threats/worst moment, the latest 15 leak events, and scheduled action outcomes. Defeat freezes the track before native `UnityToSimulation.Lose` cleanup; pre/post leak hooks retain type, properties, location, expected native modified leak damage and actual native health delta. Health delta can include overkill below zero.

Explicit same-round Sandbox replay starts a fresh sampler rather than reusing the previous attempt. Scheduled actions that expire when the next round starts are appended to the matching retained terminal report, within its action limit; previously published snapshots remain immutable.

`coverage` distinguishes sampled values and missing data. `estimatedRemainingScheduledSpawns` estimates uniform emissions within native group windows; it is not an exact runtime spawn count. `spawningComplete` and last-spawn duration describe spawning, not damage dealt or likelihood of winning. No RBE-popped percentage is fabricated. High track progress can be intentional for back-of-track defenses.

Sampled, live-observation and leak-event ordinary bloon progress share native `Bloon.PercThroughMap()`. In 56.3 this uses `(distanceTraveled + MaxDistUntilSpawn) / (MaxDistUntilSpawn + MaxDistUntilLeak)`, including native routing, not `DistanceTraveled / totalPathLength`. Values are clamped to `[0,1]`; unavailable/nonfinite progress is nullable and appears in `coverage.missing`. `coverage.progressBasis` is `native_bloon_PercThroughMap`; `progressBoundary` is `native_path_MaxDistUntilSpawn_to_MaxDistUntilLeak`. Native normal/Reverse leaks reach 1. An unknown live lane uses path index -1 rather than silently assigning lane 0.

On defeat, existing active-threat/count observation fields use the frozen report with `threatSnapshotSource: "defeat_report"`. Round waits include a matching `roundReport` in both output profiles, never a stale report from another round/match. Summary output caps composition and leaks to five entries and action outcomes to eight with omission counts; full output retains lane and worst-threat details. Lightweight `round_progress` remains free of tower/bloon scans.

### Explicit checkpoint transfer

`export_checkpoints` accepts `{includeCurrent?:true, includeSaved?:true}`. It captures current state directly without evicting local checkpoints and writes a versioned bundle only on explicit request. Current captures must be between rounds, not paused active waves or ended matches. Retained local saves require recorded round-boundary provenance. Responses contain `exportId`, relative `path`, checkpoint metadata, SHA-256 and byte size. Bundles are atomically published under `UserData/AgentBridge/exports/<exportId>.json`; no periodic disk persistence is enabled.

`import_checkpoints({exportId})` reads only that rooted safe token, validates the complete bundle, then imports its archive without changing the simulation. Imports survive loading/restarting a match within the process. `restore_checkpoint({checkpointId})` selects an imported checkpoint after a compatible map/difficulty/mode has been loaded. Label/round selectors remain available when unambiguous; an empty restore still means the latest local round checkpoint. Restore resets timing, upgrade/ability/Geraldo/Corvus schedules and telemetry. `list_checkpoints` includes `importedCheckpoints`; `delete_checkpoint({checkpointId})` releases imported memory, not the disk bundle.

Restore accepts an object containing at most one of `checkpointId`, `label`, or `round`; `{}` alone selects the latest local round checkpoint. Unknown or duplicate fields, wrong types, empty selectors, and nonpositive rounds return `INVALID_ARGUMENT` rather than selecting another checkpoint. Supplied checkpoint labels must contain 1–128 UTF-16 code units and no control characters. Omit the save label for round-keyed storage; the same label bounds apply to save, restore, delete, and transfer.

Transfer limits: 128 entries per bundle/imported registry, 512 KiB per native payload, 8 MiB per bundle. Native saves must match BTD6 56.3/model version 7; bridge module identity is recorded but may differ after a bridge update. SHA-256, duplicate-field, type-graph allowlist, path/reparse and compatibility checks fail explicitly. Unsupported native save types are rejected rather than deserialized permissively. Persistent native save objects may be retained at a boundary; active-bloon snapshots are not supported by the transfer format. Import collisions/capacity failures never partially replace existing checkpoints.

Capabilities `scheduledUpgrades`, `geraldoShop`, `corvusSpells`, `roundInsights`, and `checkpointTransfer` identify loaded bridge support. Updated adapters reject unsupported mutations before submission; reconnect the MCP host after rebuilding the adapter to refresh its running code and tool schemas.

### Cash projections

`get_projected_cash` requires an active match between rounds. `targetRound` is inclusive, bounded to 200; `fromRound` defaults to the current round. A different `fromRound` requires explicit nonnegative `currentCash` representing cash at that hypothetical starting point. Active or paused waves return `ROUND_ACTIVE` rather than counting already-earned income again.

Baseline pop cash is the sum of each bloon's native `DistributeCashModel` cash, super-ceramic `additionalCash`, and recursively spawned children, multiplied by the active `IncomeSetModel.IncomeMultiplierForRound(round - 1)`. Round rewards come from active `BonusCashPerRoundModel.GetCashForRound(round - 1)` models, not a hard-coded `$100 + round` formula. Mode modifications already applied to these models are not applied again. Fractional income is not floored; reported amounts retain six decimal places. The response exposes `incomeThresholds` and `finalIncomeMultiplier` from the active model.

`baselineIncome` reports pop cash, round rewards, their total, and baseline cash at the start/end of the target round. `towerIncome` reports a separate estimated total, per-tower inclusions/exclusions, and assumptions. The combined balances are named `estimatedCashAtStartOfTargetRound` and `estimatedCashAtEndOfTargetRound`. Each `breakdown` row contains its round, income multiplier, pop cash, round rewards, baseline income, tower-income estimate, and estimated ending cash. Threat milestones are no longer duplicated here; use `round_info`.

`confidence` is `supported`, `estimated`, or `unsupported`. A supported baseline assumes all scheduled bloons and descendants are popped without leaks or regrow farming, with unchanged economic rules. Tower estimates assume unchanged current effective models and collection of ground drops. Bank deposits/interest are not spendable income; future withdrawals, ability activations, attack-dependent cash bonuses, purchases, sales, and future buff changes are excluded.

Unknown economic behaviors, unverified per-bloon adjustments, Double Cash, active dynamic simulation cash modifiers, and generated waves are explicitly reported in `unsupportedReasons`. Unavailable amounts and dependent balances are `null`, not zero or standard-mode estimates. Known independent components may remain numeric. Apopalypse does not use the fixed round set or ordinary round-end rewards; its future pop cash is unsupported. Fixed-round forecasts use the active round-set length, not an assumed freeplay generator.

## UI interruptions and responses

`status`, `observe`, and `round_progress` require `ui: { autoHandlingEnabled, ready, blocker }`. `ready` is true exactly when `blocker` is null. A blocker contains `id`, `kind`, `screen`, `state`, nullable `reason`, `title`, and `body`, advertised `actions`, tower `choices`, and nullable `selectedChoice`. States are `waiting`, `acting`, `blocked`, and `failed`; kinds are `popup`, `tutorial`, `level_up`, `tower_unlock`, `rewards`, `transition`, `menu`, `startup`, and `unknown`.

Surface availability is part of readiness. Before game initialization, `ui` reports a `startup` blocker. Once initialized, no current menu and no active match reports a `transition` blocker with a non-null explanatory `reason` and empty `actions`. Inactive main-menu/map-selection surfaces and an `InGame` menu without an active match are likewise non-ready. Ordinary active gameplay may have no menu object; it remains ready unless a popup or native menu transition blocks it. Engine initialization and missing-menu availability use distinct blocker identities, so real startup progress starts a new readiness window. Persistent unavailability follows the existing per-step timeout, and the blocker clears when a usable surface appears. No new wire fields or action kinds are introduced.

`start_match` accepts boolean `autoHandleUi` (default true), authorizing allowlisted gameplay tutorial acknowledgements, level-up acknowledgements, and recognized informational reward panels only during the agent-started match. Normal game callbacks and panel readiness are preserved. Main-menu rewards, unknown dialogs, and tower-unlock choices are never automatically dismissed. Restarting the same match preserves authorization; returning to the main menu ends it.

`respond_ui` takes `{ blockerId, action, value? }`. `action` must be advertised by the current blocker: `confirm`, `cancel`, `next`, `select_tower`, `unlock`, `back`, `freeplay`, `home`, `restart`, `collect`, or `play`. `select_tower` requires `value` from `choices`, different from `selectedChoice`. Success returns `{ accepted: true, blockerId, ui }`; this acknowledges dispatch, not completion. Observe the subsequent state before another action.

Stale IDs return `STALE_UI_BLOCKER`; unavailable actions/selections return `INVALID_UI_ACTION`; transitioning, already-acted-on, or failed targets return `UI_NOT_READY`. An action exception returns `UI_ACTION_FAILED`, which does not establish that no mutation occurred. Each UI step receives at most one action; 10-second completion and 15-second readiness timeouts or a detected cycle report failure without automatic retries. A readiness-only timeout can recover after the native control becomes stably interactable, because no action was issued. Action failures remain single-shot.

Native continuation handlers cover level-up Monkey Money and Monkey Knowledge (`next`), hero-unlock splashes (`next`, explicit), victory statistics (`next`) followed by victory choices (`freeplay`/`home`), defeat (`restart`/`home`), and collection events (available `collect`/`play`/`back`). Restart confirmation is a separate popup action. Victory statistics and final choices have distinct blocker identities. Click-to-continue rewards can keep a parent menu transition open while awaiting their native click; that parent transition is not used to suppress their acknowledgement. Generic `back` uses the normal `CloseCurrentMenu` path, not keyboard/gamepad navigation or forced closure. No desktop coordinates cross this protocol.

A completed explicit `cancel` or `back` transition clears manual decision history so the returning parent can accept a fresh decision under its new blocker ID. Automatic acknowledgement history remains protected against cycles. Failed or still-in-flight cancellations do not reset history.

`start_round` and `ensure_main_menu` reject obstructing UI with `UI_BLOCKED`. The adapter waits through known automatic UI before starting a round and checks readiness before requested speed changes. `onMainMenu` excludes reward/unlock screens and requires unobstructed main-menu/map-selection UI. The blanket `dismiss_popup` command is removed; clients must use targeted responses rather than forcing menus closed.

`ensure_main_menu` is idempotent on an already-ready `MainMenu`: it does not re-enter the native menu transition. From an active match it initiates native `Quit` without also issuing `GoToMainMenu` in the same request. Its `{ onMainMenu, inGame }` result describes the immediate state, not a completed asynchronous transition; poll `status` until `onMainMenu` and `ui.ready` are true before starting another match.

## Current state snapshot

`state.json` contains the latest `status` and lightweight `progress` payloads, not a full observation. Captures occur on the game thread at most once per second; the worker publishes them atomically. The snapshot is advisory; an adapter that needs a request-correlated response must use `inbox/` and `outbox/`.
