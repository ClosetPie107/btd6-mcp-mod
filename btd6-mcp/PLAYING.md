# Playing BTD6 through MCP

## Role and interface

Your task is to play BTD6, not develop or repair the framework. Follow this guide together with the user's requested scenario.

- Use the registered `btd6_*` MCP tools through the native `btd6-mcp` adapter.
- Do not create a custom CLI, run ad hoc control scripts, or read/write the bridge mailbox directly. The adapter provides response validation and round-completion waiting.
- If the MCP tools are unavailable, report the integration problem. Do not build a replacement transport.
- After framework updates, refresh the MCP session. Confirm `btd6_respond_ui` is available; do not use an old session exposing only `btd6_dismiss_popup`.
- Do not modify source, build, deploy, install mods, switch research/normal modes, run the live verification harness, or provision the profile. Report framework failures with evidence instead.
- Only one agent may control the game. Do not compete with another agent or human controlling the current match.

## Run category

For the current initial strategy-development phase, default to a **checkpoint-assisted strategy-search run**: saving and restoring checkpoints to correct mistakes is authorized without asking for each retry. Restarting the requested match with a revised strategy is also authorized unless the user requests a single attempt or otherwise limits restarts. Keep the requested map, difficulty, mode, hero constraints, and normal gameplay budget restrictions. This does not authorize replacing an unrelated match, restarting the game process, or changing the requested rules. If the user requests an unassisted run, follow the ordinary-completion rules instead. Other research controls still require explicit authorization.

### Checkpoint-assisted strategy search (current default)

Use checkpoints to revise purchases, placement, targeting, or strategy without replaying the entire opening. Start these runs with `checkpointPolicy: "assisted"` (the default). The bridge automatically retains the latest next-playable-round checkpoint and permanent five-round anchors (after rounds 5, 10, 15, and so on). The round result reports the latest checkpoint as both `nextPlayableRound` and `lastCompletedRound`, preventing off-by-one restore mistakes. This is not permission to bypass the CHIMPS budget: each restored attempt must succeed using the cash and legal actions available in that state.

1. **Add strategic saves before commitments.** Automatic anchors provide coarse rollback. Before a major purchase, strategy transition, or uncertain threat between anchors, call `btd6_save_checkpoint({ "label": "before_midgame_commitment" })` before spending.
2. **Keep strategic anchors and reuse tactical labels.** Custom checkpoints are bounded to 50 in memory. Labels are case-insensitive; overwriting refreshes the timestamp. Reuse a tactical label such as `"tactical_attempt"` rather than creating one per retry. Automatic round anchors are managed separately.
3. **Reassess after five failed attempts with substantially the same core composition.** Count failures across the strategy branch, including different rounds. Changing checkpoint labels, replaying an earlier round, adding minor stopgaps, or clearing an already-beaten round does not reset the count. Five failures trigger an explicit escalation decision, not an automatic restart: before every further tactical retry, identify the observed failure, the specific correction, and evidence that it addresses the cause. Start a new branch count only when materially revising the core build or spending plan; retain the previous branch's failures and lessons.
   - *Track progress is location, not remaining health:* A leak near the exit does not by itself distinguish insufficient damage from missing detection, an immunity, poor targeting, lost ability uptime, or inadequate cleanup. Timing and targeting can matter; continue a tactical retry only with a specific change and evidence it addresses the failure.
   - *Measure progress against the diagnosed failure:* Breaking a previously unbroken BAD is meaningful progress, but creates a separate child-cleanup requirement. A slightly later leak of the same threat does not alone justify another retry. Re-clearing rounds already beaten is not evidence that the final build is becoming viable.
   - *Budget reality check:* Price a legal counter using the restored state's cash and actual upgrade quotes. There is no universal cash cutoff for a recoverable run. In CHIMPS, money already spent cannot be recovered by selling, so compare an affordable correction against rolling back before the expensive commitment.
   - *Whole-run validation gate:* After the five-failure threshold, a plausible local correction is insufficient by itself. Before another tactical retry, identify the revised final defense, its remaining purchase costs and deadlines, and the evidence that it can beat the remaining threats through the final round. Apply the [endgame-validation rules](#endgame-validation) below; distinguish demonstrated coverage from untested assumptions. If no affordable, evidence-backed path remains, return to a strategic anchor and revise the spending plan rather than continuing to adjust the current round's timing.
   - *Escalate when corrections are exhausted:* If no evidence-backed tactical correction remains, restore an earlier strategic anchor where the relevant cash is still uncommitted and revise the composition. If no suitable anchor remains, restart with a revised build when the run category permits it; otherwise report the defeat or blocker. Do not continue an exhausted branch merely because another timing adjustment is possible.
4. **Diagnose before retrying.** Read the returned `roundReport`: leaks identify the triggering bloons; active counts/composition show what remained; pressure and worst-moment data also describe successful rounds. Check `coverage` before interpreting missing or sampled values. Record the failed round, defense, suspected cause, and intended correction. Consult the strategy record before acting; do not repeat a hypothesis already tested unsuccessfully under equivalent conditions. If the late-game budget is broken, roll back before the spending that caused it, not merely to the last round.
   - Separate the final health-damaging leak from remaining workload. A non-camo Green triggering CHIMPS defeat with many blimps still alive is not evidence that the surviving blimps caused a detection failure. On terminal rounds, `postSpawnPressure` reports sampled MOAB and Ceramic persistence after the native spawn schedule ended. Long post-spawn MOAB duration plus late Ceramic pressure supports a late-layer-processing diagnosis; it does not by itself prove which tower, targeting choice, or immunity caused it.
5. **Select and restore explicitly.** Terminal round results include a bounded `recovery` inventory with exact `{ "round": ... }`, `{ "label": ... }`, or `{ "checkpointId": ... }` selectors. Prefer the latest viable anchor, or call `btd6_list_checkpoints({})` when no recovery inventory was returned or older anchors are needed. Restore can recover from defeat while the match remains loaded; do not quit or restart first and destroy local saves.
6. **Verify the restored state.** `btd6_restore_checkpoint` waits for a between-round state and returns `stateReady`, `schedulesCleared`, and compact `state` containing fresh tower IDs, cash, lives, upgrades, abilities, and UI. Act only when `stateReady` and `state.ui.ready` are true. If not, inspect the returned blocker and call `btd6_observe`; do not assume a checkpoint is a frame-exact active-wave snapshot. Prefer between-round saves.
7. **Revise and continue.** Update the long-term purchase schedule using the restored budget, make the correction, and resume normal round execution. Maintain one compact strategy record in your working notes: core build, reserved purchase budget and deadlines, available rollback anchors, branch failure count, failed hypotheses with checkpoint/round/change/outcome, and the next escalation decision. Update it after each attempt and carry it into context-compaction summaries or handoffs; restoring a checkpoint or restarting a match does not erase these lessons. Checkpoint rollback must not be used to accumulate duplicated income or rewards; report unexpected state instead.

`btd6_save_checkpoint({})` saves a round-keyed checkpoint. Prefer explicit labels or listed round numbers when restoring; an empty restore selects the highest local saved round. These captures remain memory-only. Before an intentional process restart, explicitly call `btd6_export_checkpoints({ "includeCurrent": true, "includeSaved": true })` between rounds and retain the returned `exportId`. After restart, call `btd6_import_checkpoints({ "exportId": "..." })`, load the compatible map/difficulty/mode, then restore an imported `checkpointId`. Import does not alter the simulation. Disk transfer supports validated round-boundary native saves, not arbitrary paused-wave snapshots. Delete unused imported entries with `btd6_delete_checkpoint({ "checkpointId": "..." })`; this does not delete the exported file.

Defeat during an authorized checkpoint attempt is a failed branch, not necessarily the end of the run. Prefer a suitable earlier anchor over replaying the opening. When a fresh match is necessary and authorized, record the failed branch and revised build first, then use `btd6_restart_match` or the currently advertised native restart UI action. Match restart clears local checkpoints and schedules: export any useful anchors before replacement when a supported export is possible, and retain failed-attempt evidence and strategy notes. Observe and verify the restarted scenario, initial economy, and fresh tower IDs before purchasing. For a single-attempt run without restart authorization, report the defeat or blocker once useful checkpoint corrections are exhausted. Report the final result as checkpoint-assisted and disclose failed branches and restarts; do not claim an unassisted or black-border CHIMPS completion.

### Ordinary completion

- Follow the requested map, difficulty, mode, and hero. If unspecified, use Logs / Easy / Standard.
- Use ordinary player actions: placement, upgrades, selling, targeting, abilities, collecting income, fast-forward, and round starts. Read-only planning tools are allowed.
- Start with `checkpointPolicy: "none"`. Do not save or restore checkpoints, set or advance rounds through research controls, spawn or clear Sandbox bloons, provision the profile, or use other research mutations to obtain a win.
- Do not automatically restart a defeated match. Report the attempt before starting another unless the user authorized repeated attempts.
- This is a fully provisioned research profile, not a fresh-account benchmark. Disclose that distinction and the automatic-collection setting.

### Authorized research experiment

- Use only the research controls authorized by the user for the experiment.
- Label checkpoint retries, round manipulation, Sandbox testing, and other research assistance explicitly. A checkpoint-assisted result is not an ordinary unassisted completion.
- If assistance has already occurred, retain that fact in the result even if subsequent play uses only normal actions.
- Keep raw tool evidence separate from model-authored strategy notes.

## Startup

1. Call `btd6_status` and `btd6_observe`. Record the loaded `moduleVersionId`, BTD6 version, selected hero, automatic-collection setting, and current match/UI state.
2. Do not replace an unrelated active match or restart the game without authorization. If this is the requested ongoing attempt, continue from its observed state.
3. For a new attempt, start from an unobstructed main menu. Honor a user-specified hero. Otherwise treat the selected hero as provisional until the map assessment below; do not inherit a previous match's hero as a strategy decision. Call `btd6_start_match` with the requested scenario, `autoHandleUi: true`, and the run's explicit `checkpointPolicy`.
4. Wait until observation shows an active match with the requested `mapId`, human-readable `mapName`, mode, and `ui.ready`. A successful start request is not proof that loading completed.
5. Verify the actual mode and economy before purchasing. A fresh CHIMPS match should report `mode: "CHIMPS"`, `difficulty: "Hard"`, round 6, `endRound: 100`, $650, and one life. Impoppable is a different mode, not an alternative CHIMPS difficulty label. Use final placement quotes and placed-tower upgrade costs rather than unrounded catalog model values. If the setup is inconsistent, report it instead of adapting the strategy to an unintended ruleset.
6. Before the first purchase or round, complete the map-first hero and defense assessment below. When continuing an existing attempt, assess the current defense without replacing the match or assuming its hero can be changed.

## Map-first hero and defense selection

**Use the layout to rule strategies in or out, not just to locate a tower already chosen.** Call `btd6_get_map_layout` before committing the opening. Inspect the tactical image together with `trackGraph.routingPolicy`, route/edge traffic, terrain, and blockers. If the image is unavailable, use `format: "geometry"`; do not claim visual inspection. Reuse the assessment until geometry or relevant routing changes.

1. **Describe the coverage problem.** Identify entries/exits, travel directions, shared track sections versus disconnected lanes, traffic shares, legal placement space, and line-of-sight restrictions. Distinguish simultaneous split traffic from round-alternating routes; consult `btd6_round_info` or the layout's `round` option for relevant future rounds. A crossing on the image is not necessarily a shared route, and the opening round's active paths need not describe the entire run.
2. **Compare heroes against that problem.** Unless the user fixes the hero, compare at least two plausible heroes before committing. Use live catalog/stats for unfamiliar costs, range, attack behavior, and abilities. Explain their intended role, useful attack uptime on each route, early affordability, and contribution to the endgame. Familiarity or a general tier ranking is not map-specific evidence. Global range does not automatically bypass blockers, and support heroes need useful recipients rather than direct track coverage.
3. **Prove the proposed position is useful.** For a short-range damage hero, request native-valid placement candidates with `rankingStrategy: "trackCoverage"` and inspect their per-route coverage. Judge which track sections are reachable and how long threats can remain in range; do not invent exact firing times from a static image. The highest-ranked candidate may still be inadequate, and total coverage can hide an uncovered lane. Account for LOS and attack behavior, not only a range circle. If the hero serves only one lane, name and budget the defense for the others. Reject the choice if that split investment undermines the saving plan; do not assume an ability compensates without checking its targeting, availability, and cooldown.
   Placement summaries omit path intervals. When route identity or covered sections matter, request `outputProfile: "full"` with a small `limit` and inspect `trackCoverage.paths` alongside the layout. `detailsOmitted: true` is not evidence of zero coverage. These are bounded placement-search results for the current occupied map, not an exhaustive optimum or a native damage/LOS measurement.
   Coverage search seeds bends and refines candidates, but can still miss narrow legal pockets. Compare the returned positions with useful bends on the layout; use a focused `near` query or a direct `can_place_tower` check when warranted. Shortlists suppress nearby alternatives, so fewer than `limit` results does not imply there are no other legal centers. Keep `trackCoverage` for both targeted and radial attackers; inspect angular coverage as an additional clue for Tack-style attacks, not as a damage estimate.
4. **Record the decision before spending.** Keep a compact map assessment in the strategy record: routing and constraints; chosen hero and proposed position/role; covered and uncovered routes; the budgeted answer to each gap; and why the alternative was rejected. State what the layout changed or ruled out. For a fixed hero, skip the alternative selection but explicitly budget around its limitations. Do not turn this into a map blacklist: a lane-specific hero can be justified by the complete defense.
5. **Resolve provisional selection safely.** The live layout requires a loaded map, so initial hero selection can precede inspection. If it proves unsuitable, replace only the requested attempt when its restart permissions allow: return to the main menu through native tools and start the same scenario with the revised `hero`, then verify the scenario and initial economy again. Do not assume `select_hero` changes an already-loaded match's hero or that a plain restart selects a different hero. For a single-attempt/no-restart run, do not discard the attempt for scouting; retain the legal selection and plan around its limitations, or obtain permission before replacement. Inspection is not authorization to replace another player's match.

## Long-term strategy and budget

**Plan to beat the entire mode, not just the next round.** Surviving the current round is necessary but insufficient: repeated emergency purchases can leave a defense unable to afford its late-game win condition. Establish a concrete strategy before the first purchase, or reconstruct one from the existing defense when continuing a match.

- **Choose an endgame defense from the map assessment.** Identify the main damage tower(s), intended upgrades/crosspaths, hero role, support, control, and ability plan. Explain how they cover both grouped bloons and high-health blimps on every relevant route. Do not assume one strong tower handles every lane, immunity, or threat.
- **Work backward through the stages.** Plan an affordable opening, a midgame defense that can save toward the core upgrades, and the late-game transition. Give each stage target purchases, approximate purchase rounds, and the threats it must cover. Early towers should contribute to the final defense or have a justified, limited cost as temporary support.
- **Set coverage deadlines.** Check upcoming round information rather than reacting after a weakness appears. Account for camo, lead, purple and other immunities; the first MOAB; dense ceramic waves; BFBs/ZOMGs; and, when the mode reaches them, super ceramics, DDT waves, dense fortified blimps, and the round-100 BAD. Verify that damage, detection, pierce, control, and ability availability cover the relevant threats before their rounds.
- **Make the budget feasible at every stage.** Use live prices for the actual difficulty, remaining upgrade costs, and projected cash to estimate when each key purchase becomes affordable. Maintain a compact purchase schedule with the target round, cost still needed, projected cash, and remaining margin. An affordable final build is not enough if its intermediate defense cannot survive the saving period.
- **Respect CHIMPS economics and budget for both wave clear and blimp damage.** In CHIMPS, plan around the finite cash available from normal progression through rounds 6–100. Do not assume farming or other bonus income, selling/refunds, Monkey Knowledge, powers, or paid continues can fund or rescue the build. Authorized checkpoint retries can revise earlier decisions, but cannot increase the budget of the restored state. Money spent on a stopgap cannot be recovered by selling it. Do not treat generic income projections as spendable unless that income is actually permitted in the active mode.
  - *Wave clear is not proof of BAD coverage:* Spectre, Spirit of the Forest, and Bloon Solver have different damage profiles; none should be dismissed solely by its role or price. Budget and verify damage against the actual round-100 BAD and its children, including round scaling, available firing time, support, and ability cooldowns. Add dedicated burst or sustained blimp damage if needed, without neglecting DDT detection and ceramic cleanup. Stall that works on other blimps does not establish BAD control.
- **Protect the saving plan.** Do not spend merely because cash is available. Before an unplanned purchase, identify the concrete coverage gap it fixes, compare cheaper targeting/ability or purchase alternatives, and calculate whether it delays a required upgrade beyond its deadline. Reserve affordable contingency money where possible; do not assume speculative future earnings are already available. Update the final roster and budget after deviations, and renew [endgame validation](#endgame-validation) when its assumptions materially change.
- **Plan placement for the final build.** Reserve legal space and useful track coverage for larger towers, support ranges, and synergies. Avoid an opening layout that prevents the intended late-game placements.
- **Rank coverage, not merely proximity.** For short-range or radial attackers, use `rankingStrategy: "trackCoverage"` and evaluate per-route gaps, not just the winning score; best available does not mean sufficient. For a Village or Alchemist, pass the intended recipient IDs as `coverTowerIds` with `rankingStrategy: "supportCoverage"`, then prefer candidates with no `uncoveredTowerIds`. After placement, read `supportCoverage.strategicWarning` or call `btd6_inspect_support_coverage`; geometric coverage does not prove native buff eligibility, so verify important recipients with `btd6_inspect_tower`.
- **Separate camo acquisition from collision.** Read `poppingCapabilities.camo.canDamageCamo`, its evidence and per-weapon branches before buying detection. `needsDetection: false` does not itself mean camo damage: manual Mortar/Dartling aim and Heli/Ace movement remain subject to projectile filters. Native 56.3 examples are innate Spike Factory collision, Mortar 0-0-1, Heli 0-2-0, Dartling 0-1-0 and Ace 0-2-0. Verify actual placed buffs with `btd6_inspect_tower`; do not add Radar to an already camo-capable spike defense solely because something leaked.
- **Replan deliberately.** Reassess at stage transitions, before major purchases, and after unexpected weakness or spending. Update the same strategy record used by the recovery workflow with coverage gaps, next purchases, saving targets, and budget implications. If the original build is no longer feasible, choose and budget a coherent alternative rather than accumulating unrelated emergency towers.

Use the requested mode's actual final round and restrictions. Apply this planning discipline to every run; apply the strict CHIMPS budget and no-selling assumptions when playing CHIMPS.

### Endgame validation

Treat endgame validation as conditional on a specified build, budget, and starting state. Material deviations require renewed validation: testing one defense does not validate a different defense eventually reached through emergency purchases.

- **Test the proposed endpoint when Sandbox testing is authorized.** Preserve the live run with a round-boundary export before replacing it. Match the map, difficulty prices, legal total budget, hero level, upgrades, placements, support, and relevant round scaling; verify Monkey Knowledge is disabled for CHIMPS tests. Record the setup, rounds tested, actual outcomes, and any unmatched conditions. Checkpoint assistance alone does not authorize Sandbox or profile changes; if matching conditions cannot be established with authorized tools, record that limitation rather than claiming a representative pass.
- **Revalidate material changes.** Purchases that displace required endgame damage or support, miss a purchase deadline, or alter required ability availability invalidate the affected conclusions. Revise and retest the plan where authorized; do not retain a blanket "tested" label. Without testing authorization, use read-only evidence and explicitly retain uncertainty.
- **Validate the route and transitions too.** An endpoint test does not prove the intermediate defense survives its saving periods. Verify purchase milestones during the buildup and test critical consecutive rounds with realistically attainable starting cooldowns and persistent state. Passing rounds separately with fresh abilities does not establish that the sequence works; a Sandbox pass is not a completed run.

For Paragon, Temple, or Monkeyopolis planning, use the read-only inspection tools before committing, then re-inspect after changing the sacrifice set or support. Paragon projections require a placed Tier 5 for a native price quote; check `formulaConfidence` and milestone reachability. `excludeTowerIds` is hypothetical and does not prevent actual sacrifices. Temple category ties and final VTSG prerequisites may remain unknown; outside-range Anti-Bloon/Legend of the Night positioning alone is not proof of formation. Monkeyopolis excludes Tier 5 farms, and its standalone-income/payback comparison does not include bank balances, active buffs, collection timing, or mode restrictions. Read the returned assumptions rather than treating every estimate as spendable cash. Placement inside a model-range circle does not itself prove support or sacrifice eligibility.

For unfamiliar bosses, read `btd6_boss_catalog` for the game's own descriptions, then use `btd6_inspect_boss` and `observe.bosses` for current defenses and skull progress—even between rounds. Select instances with their runtime `id`. Check tower-category immunity separately from invulnerability, damage properties, and armour. `null` is unknown; unfamiliar behavior is not proof that a boss lacks special mechanics. Do not sum segment HP into boss HP or mistake repeating health triggers for skulls. Full tower-stat/inspection output exposes nested `damageSources`; request it when investigating conditional damage. Those sources and Paragon `paragonBossDamage` are components, not a final boss-DPS estimate; avoid double-applying degree scaling already reflected in effective modifiers.

## Gameplay loop

The output-profile guidance below describes the updated adapter source. An already-running MCP process keeps its loaded implementation until rebuilt and reconnected; follow its mounted tool schemas if they differ. Do not reconnect during an active run merely to change verbosity defaults.

1. **Observe and plan.** Prefer the default summary observation for routine decisions; it retains resources, actionable tower state, hero/abilities and UI/boss safety. Do not request another observation after every clean round if the round result and your current roster suffice. Request `outputProfile: "full"` for lifetime statistics, retained reports or detailed diagnostics. Consult `btd6_get_map_layout`, `btd6_tower_catalog`, `btd6_tower_stats`, `btd6_inspect_tower`, `btd6_round_info`, and `btd6_get_projected_cash` as needed. Filter catalogs with `towerType` to obtain one tower's upgrade details; avoid repeatedly fetching the full catalog. `btd6_get_map_layout({ rangeTowerIds: [...] })` can add bounded native range/LOS triangles and per-attack wall flags; these describe sampled native range/LOS, not complete damage/projectile/subtower coverage. Check the next threats against the long-term purchase schedule; decide whether to buy or keep saving.
   For cash planning, project only between rounds and check `baselineIncome.confidence` first. Use the baseline balances for a budget excluding tower-generated income; use `estimatedCashAtStartOfTargetRound` / `estimatedCashAtEndOfTargetRound` only after reading `towerIncome` inclusions, exclusions, and assumptions. `null` means unavailable, not zero. Do not budget from unsupported generated-wave forecasts or silently substitute normal-mode payouts. Re-project after purchases or income-buff changes; provide explicit `currentCash` when modeling a starting round other than the current one.
2. **Validate and act.** Use map-relative coordinates, not screen pixels. Use placement checks or placement-spot discovery before purchasing. Use current observed tower IDs and tool schemas; do not guess identifiers or argument conventions.
   Placement discovery validates geometry, not affordability: use `can_place_tower` for a final price when needed. Use `nextUpgrades` for path, semantic upgrade name, availability, and live cost; `crosspathSlotsRemaining` reports the remaining legal secondary-path tiers once a main path is chosen. Batch a planned sequence using `btd6_upgrade_tower({ "towerId": "...", "upgradeSequence": [1, 1, 1, 1] })` to buy four middle-path upgrades. This is a purchase sequence, not a final-tier array.
   For tight timing, use the same upgrade tool with `"round": 98, "delaySeconds": 12.5`, or `"whenAffordable": true`. Conditions combine: timed affordability expires at target-round end; affordability-only persists across rounds. Zero seconds waits for round start. Scheduled work runs without further model polling and freezes when paused/UI-blocked. Inspect `scheduledUpgrades` and use `btd6_cancel_scheduled_upgrade` to stop remaining purchases. Restore/restart clears schedules; re-plan using fresh tower IDs. No scheduling options means an immediate purchase sequence, still convenient between rounds.
3. **Run rounds.** For one tactical round, call `btd6_start_round({ "waitForCompletion": true })`; these are the defaults. For a stable stretch, call `btd6_run_rounds({ "count": 5, "stopBeforeRounds": [40] })`. The bounded batch stops before requested strategic rounds and on every defeat, victory, timeout, match replacement, or UI blocker; every underlying round remains a separate action-journal entry. Use batches only across rounds that need no purchases, targeting changes, ability schedules, or assessment.
4. **Assess the result.** Read top-level completion, `statusReason`, lives, cash, `checkpoint`, and `roundReport` when available. On terminal results, inspect `postSpawnPressure` and `recovery`; do not infer cause from the final leak alone. `checkpoint.nextPlayableRound` is the restore key; `lastCompletedRound` is the round just cleared.
5. **Continue to an explicit terminal result.** A cleared intermediate round, idle game, or timeout is not victory.

Schedule known ability/upgrade/Geraldo item timing before starting the round, then use the normal waiting call. For a genuinely reactive mid-round action, start with `waitForCompletion: false`, act, and use `btd6_wait_for_round_end`. Do not start an already active round again.

Request `btd6_round_info({ "round": 98, "outputProfile": "full" })` when you need individual spawn-group timings; default summary retains aggregate threats and routing. `round_info` times and `schedule_ability.delaySeconds` use simulation seconds, not wall-clock time. Fast-forward changes wall-clock pacing only. The round's `durationSeconds` ends at the last scheduled spawn, not when all bloons are cleared. Budget damage coverage using `requiresLeadPopping`, which includes DDTs; `hasLead` alone identifies literal Lead bloons. Tactical coordinates use +X right/+Y down; use returned coordinates directly.

Ability activation and scheduling share typed `target` input: `point` (`x`, `y`), `tower` (`towerId`), `tower_position` (both), or ordered `points`. Read `abilities[].targeting` for the supported kind and multi-point count; omit the target only for untargeted abilities. Use the exact observed `abilityId` when possible, or `abilityIndex` (not the old scheduled `index`). Schedules pin that identity and retain their target through cooldown retries. A submitted activation does not prove a delayed mine has spawned or a relocation has finished. Inspect effects before relying on them; invalid or unsupported targets never intentionally fall back to the origin.

For Geraldo, inspect `btd6_inspect_geraldo` for native IDs, stock, prices and `targetKind`, then use `btd6_can_use_geraldo_item` before committing a target. Buy through `btd6_use_geraldo_item`, not ordinary tower placement. Tower-like items and nails/glue/blade traps need native-valid points; buffs need an eligible tower ID. Fertilizer requires an eligible Banana Farm, and Cape an eligible Dart Monkey. **Rabbit and Rejuvenation take no target:** rabbit placement is resolved automatically at Geraldo's current position.

Geraldo purchases are immediate by default, including mid-round. The same tool accepts `round`/`delaySeconds`, `delayFromNow`, and `whenAffordable`. A timed affordability wait expires at target-round end; affordability-only waits across rounds. No cash/stock is reserved, and schedules do not wait for restocking or unlocks. Inspect `scheduledGeraldoPurchases` and cancel with `btd6_cancel_scheduled_geraldo_purchase`. Prefer between-round purchases unless timing or incoming cash provides a concrete benefit. Due abilities execute before upgrades and Geraldo purchases, but a timestamp is not a guarantee an earlier ability succeeded. Treat `verification_pending` as an uncertain purchase, not permission to spend again. Restore/restart clears schedules; re-inspect tower IDs and stock.

For Corvus, use `btd6_inspect_corvus` for current mana, level unlocks, active spells, cooldowns and `canCast`/`unavailableReason`. Use `btd6_cast_corvus_spell` for kind `cast` and `btd6_set_corvus_spell({spellId,enabled})` for kind `continuous`; spellbook actions have no target. Always request an explicit enabled state, not a blind toggle. Repeated desired-state requests are harmless no-ops. Turning a continuous spell off does not require its activation mana. Ordinary hero abilities still use the existing ability tools.

Both Corvus action tools support native round timing and `whenReady`. A readiness wait can span mana shortage, an active spell, cooldown or recovery, but not a future level unlock. Timed waits expire at target-round end; readiness-only waits persist. Budget ongoing drain as well as initial mana cost. An enable request is not an instruction to keep re-enabling the spell. Inspect `scheduledCorvusActions` for eventual results; `btd6_cancel_scheduled_corvus_action` cancels pending work but does not turn active spells off. Schedules pin the current hero and are cleared by restore/restart. A `verification_pending` result or uncertain transport error is not permission to cast again with a fresh key.

For paid removals, call `btd6_inspect_obstacles`, budget the quoted price, then `btd6_remove_obstacle({ "obstacleId": "..." })`. Use fresh runtime IDs. Check charge and removal verification separately; pending or unavailable verification is not permission to repeat a purchase. Re-read map geometry and placement candidates after clearing an obstacle. This works with native CHIMPS removal economics; it does not provide arbitrary switches, dam levers or other map gimmicks.

For advanced micro, inspect `btd6_inspect_tower_micro` first. Select an advertised native mode with `btd6_set_target_priority`, then use `btd6_set_tower_target_position` for an active coordinate target. Ace `Centered` needs xx2; Heli `Pursuit` needs 2xx. Flight mode changes and coordinate changes are separate actions. Native 56.3 Spike Factory modes use IDs such as `SmartTrack` and `CloseTrack`; never assume a legacy Far mode exists. Robo/Tech Terror need a returned arm `targetIndex` and cannot share priorities. Re-inspect indices after upgrades/mode changes. For Heli patrol, `pointIndex` changes only that waypoint; inspect the returned full patrol array.

Targeting setters return applied state rather than the complete `micro` discovery payload. Read `activeTargetTypes`/`arms`/`pathModes` after a priority change, and `coordinateTargets` (including native patrol points) after a coordinate change. ## UI interruptions and uncertain outcomes

- Allow authorized informational screens to advance through the bridge's normal UI handling.
- On `ui_blocked`, inspect `ui.blocker` and its state:
  - `waiting` or `acting`: allow the transition to complete; do not issue competing actions.
  - `blocked`: understand the dialog, then use `btd6_respond_ui` with the current blocker ID and an advertised action when that action is within the user's authorization.
  - `failed`: report the reason. Do not repeat an already-issued action. A readiness-only timeout may recover when the native control becomes interactable; act only if a fresh observation advertises the action.
- Use native MCP actions, not desktop clicks: `next` advances Monkey Money/Knowledge rewards, hero-unlock splashes, and victory statistics. Victory then offers `freeplay`/`home`; defeat offers `restart`/`home`; collection events offer available `collect`/`play`/`back`. Treat freeplay and restart as decisions, not generic popup dismissal, and follow any new confirmation blocker.
- Never blindly confirm account, purchase, or destructive prompts. Ask the user when a decision exceeds the run's authorization.
- An accepted UI response does not establish that the UI finished. Re-observe before continuing gameplay.
- A stale blocker ID requires a fresh observation, not reuse of the old ID.
- After a timeout or uncertain submitted action, observe before retrying. Do not repeat an uncertain purchase. If a round remains active, wait for it rather than starting it again.
- Treat match-loading exceptions as real failures. Preserve the tool error and observed state; do not repeatedly restart, patch code, or declare the match started merely because the initial request was accepted.
- If progress is blocked by a framework failure or unsupported action, report the blocker and leave the state available for inspection. Do not manufacture a completion result.

## Completion and evidence

Continue until explicit victory or final defeat, unless the user stops the run or a genuine blocker prevents progress. In checkpoint-assisted runs, follow the recovery workflow above after a failed branch; in unassisted runs, defeat ends the attempt. Preserve the final terminal result and leave the match available for inspection unless cleanup was requested.

Report:

- Map, difficulty, mode, hero, game version, and loaded bridge `moduleVersionId`.
- Run category, outcome, last cleared round, remaining lives and cash.
- Tower strategy and important adjustments.
- UI interruptions, tool errors, unresolved blockers, and uncertain outcomes.
- Automatic collection, provisioned-profile context, and all research assistance, failed branches, checkpoint retries, and match restarts used.

Keep raw tool evidence distinct from your explanation. Do not commit runtime reports or credentials. Never call an assisted run unassisted, or an incomplete run a victory.
